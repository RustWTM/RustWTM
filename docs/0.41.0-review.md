# RustWTM 0.41.0 release scope and validation

## Scope

The CPU history graph names the process behind each sample, as Process
Explorer's graph does (#4). Protocol 20 is unchanged; a 0.40.0 service
and a 0.41.0 window work together.

- **Busiest process on the CPU graph.** Each sample the window receives
  records the process with the most CPU in it, leaving out the System
  Idle Process, next to the system history. On the Performance page,
  the label at the pointer over the CPU history graph adds that process
  and its share, for example `12:00:01 · CPU: 42.0% · chrome.exe 18.0%`,
  and the line under the graph names it while a moment is inspected.
  The record lives in the window only: the history the service sends
  when the window connects carries no processes, so those samples name
  none. The hovered sample is found on the graph's own timeline, so
  after a clock change it is never an older sample with the same time.
  No new text needs translation.

## Verification

`cargo fmt --check`, `cargo clippy --workspace --all-targets -D warnings`,
`cargo doc` with warnings denied and the workspace tests pass on the
developer host from a clean checkout (1296 passed, 23 ignored).
`scripts/ci/verify-release.ps1 -Tag v0.41.0` checks the published
assets. CI adds 0.40.0 as an upgrade baseline, with the SHA-256 of its
published MSI.

Test changes since 0.40.0:

- `wtm-gui` backend: `each_sample_records_its_busiest_process` covers
  the idle process left out, a repeated sample adding nothing, service
  history without processes, and alignment after a reset.
- `wtm-gui` Performance page:
  `inspecting_the_cpu_graph_names_the_busiest_process_of_that_sample`
  reads the line under an inspected graph, and
  `performance_cpu_hover_uses_the_sample_after_a_clock_restart` reads
  the label at the pointer after a clock restart. Both fail when the
  graph is given no process to name.

Not covered: the graph in a real window with live processes; the tests
use recorded samples.
